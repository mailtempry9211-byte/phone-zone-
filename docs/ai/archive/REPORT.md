## 2. Item-by-item (what changed and why)

### 2.1 Update guard (`POST /:table/update`) - item 1
`backend/src/routes/compat.js` now refuses, before any SQL runs, when:
* `filters` is not a non-empty array -> `400 Refusing to update without a filter...`;
* any filter names a column that is not an exact column of that table -> `400 Unknown column in filter: ...` (the filter is **not** dropped);
* any filter uses an operator outside `eq|neq|gte|lte|is|in|or` (or an `or` sub-expression outside `eq|is|ilike`) -> `400 Unknown filter operator: ...`;
* the resulting `WHERE` is empty -> `400 Refusing to update: the filter did not name a real column. No rows were changed.`;
* a key in `values` is not an exact column of the table -> `400 Unknown column in update values: ...` (this is also the A43 "column-name injection in values" defence);
* `values` contains `id` or `created_at` -> `403 "<column>" cannot be changed through the compatibility layer.`;
* the table is `audit_logs` or `files` -> `403` (items 4 and 5).

`buildWhere()` itself now calls `assertFilterColumns()` and throws instead of `continue`-ing, which is why the same protection covers delete and select without duplicated code.

### 2.2 Select guard - item 2
`POST /:table/select` goes through the same `buildWhere()`, so an unknown filter column is `400`, not a silently-ignored filter. There is no separate count route in this backend (`/api/dashboard` and the services do their own parameterised queries), so nothing else needed a change.

### 2.3 Exact column match - item 3
```js
function columnAllowed(tableName, col) {
  const cols = columnsOf(tableName);
  if (!cols) return false;
  return typeof col === "string" && cols.includes(col);
}
```
The old `col.replace(/^"|"$/, "")` quote-stripping is gone. The name that passed this check is the only string interpolated into SQL (values are always bound parameters).

### 2.4 Audit log read-only - item 4
`COMPAT_WRITE_FORBIDDEN = new Set(["audit_logs", "files"])`; `assertCompatWritable(t)` is called by insert, update and delete. `audit_logs` answers `403 The audit log is read-only. Audit rows are written only by the server.` Select on `audit_logs` is still allowed (admin-only via the existing `staff` guard); the UI reads the trail from `GET /api/audit-logs`.

## 6. Behaviour changes the owner should know

1. **A compat write with an unknown column in `values` now fails loudly (400)** instead of silently writing the valid keys. This is intentional (it is A43), and every existing update call in `src/` sends only real columns.
2. **A compat write/delete with an empty filter list is refused for every table**, not just phones. This is the item-1 requirement.
3. **An `.or(...)` search term containing a comma** can now produce a 400 from the compat layer (the expression parser splits on commas). No existing screen builds such an expression from free text without the user typing a comma; a comma in the search box will show an error instead of a partial match. Not worth adding an escaping layer for a single-user desktop app, but it is a real difference.
4. **Events that used to answer 400 in the compat layer now answer 403** when the table itself is refused (`audit_logs`, `files`, or a non-deletable table). A client that treated 400 as "user error" will see 403.
5. **`DatabaseTab` no longer imports a bare `.json`** - the toast tells the owner to use Backup & Restore, which restores the SQLite database and `storage/` through the backend.

## 7. Known limitations / honest notes

* The `A41` forged-row read returns **HTTP 500** (`Path traversal blocked`), not 404: `resolveStoragePath()` rejects the path before the file is opened, and that rejection is a generic error. The bytes are never served and nothing is logged in the response body beyond the standard "Something went wrong" message, but a 500 for a deliberately malicious row is noisier than a 404. Fixing the status would mean touching `backend/src/config/paths.js` / `storageService.js`, which are outside this stage's file list.
* The A41 forged row is written **directly into the temp SQLite database** by the harness, i.e. with the app bypassed. It proves the read endpoints are safe even if a row is corrupt; it does not prove that a normal user can create such a row (the compat layer now refuses to, item 5).
* `audit_logs` select is still readable through the compat layer by an authenticated admin. That is required by the audit screens; the stage only makes it **immutable**, not invisible.
* The verify harness always exits 0 by design (so `.bat` reaches `pause`); read the `SUMMARY` line, not the exit code.
* ESLint still reports the pre-existing `no-explicit-any` style warnings (~188). Not an assertion, build unaffected.
* Nothing from Stage 2/3A/4 exists: no `electron/`, no installer, no tunnel, no repairs UI, no WhatsApp. The `main` field of `package.json` still points at `electron/main.cjs` (the known B5 blocker, Stage 3).
